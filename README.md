# Финансовый трекер

Веб-приложение для управления личными финансами: счета, транзакции, категории, бюджеты. С поддержкой аудита действий пользователей, метрик, оптимистичной блокировки на финансовых операциях, импорта транзакций из банков (T-Bank) и REST API для конвертации валют.

## Возможности

- **Управление счетами** — CRUD, пополнение, снятие, баланс по валютам, редактирование.
- **Транзакции** — доходы/расходы с категориями, фильтрация, группировка по счетам.
- **Бюджеты** — установка месячных лимитов на категории, отслеживание трат с конвертацией расходов в разных валютах в рубли.
- **Аудит** — асинхронное логирование операций создания/изменения/удаления с деталями.
- **Админ-панель** — управление пользователями, ролями, просмотр журнала аудита.
- **Курсы валют** — REST API для получения курсов и конвертации сумм (см. [Swagger](#swagger--openapi)).
- **Интеграция с банками (T-Bank)** — импорт транзакций дебетовых/расчётных счетов через T-API, только чтение. Готово на уровне сервисного слоя и покрыто тестами; UI для привязки счёта и запуска синхронизации ещё не реализован (см. [Интеграция с банками](#интеграция-с-банками-t-bank--t-api)).
- **Безопасность** — Spring Security (сессионная аутентификация, form login), пароли хешируются BCrypt, защита от IDOR на уровне владения счетами/транзакциями.
- **Целостность данных** — оптимистичная блокировка (`@Version`) на счетах защищает от потери параллельных изменений баланса.

## Стек технологий

- Java 17, **Spring Boot 3.5**
- Spring Data JPA + Hibernate (связи между сущностями — `FetchType.LAZY`, где не указано явно `JOIN FETCH`)
- Spring Security
- **PostgreSQL 16** + **Liquibase** (управление схемой БД; MySQL не используется и не поддерживается)
- Thymeleaf (веб-интерфейс)
- Lombok, MapStruct
- springdoc-openapi (Swagger UI)
- Micrometer + Prometheus + Grafana (метрики и мониторинг, actuator на отдельном непубличном порту — см. [Мониторинг](#мониторинг-prometheus--grafana))
- WebClient (реактивный HTTP-клиент) — для внешних API курсов валют и T-Bank
- JUnit 5, Mockito, **Testcontainers** (интеграционные тесты с реальным Postgres), JaCoCo (покрытие)
- Docker / Docker Compose (с healthcheck'ами для БД и приложения)
- Maven

## Быстрый старт (Docker)

Самый простой способ поднять всё окружение целиком:

```bash
cp .env.example .env
# отредактируйте .env: DB_USERNAME, DB_PASSWORD, DB_NAME должны совпадать
# с тем, что укажете — они прокидываются как в приложение, так и в
# инициализацию контейнера Postgres

docker compose up -d --build
```

Приложение будет доступно на **http://localhost:8080**.

Тестовые учётные записи (созданы seed-данными Liquibase):

| Email | Пароль | Роль |
|---|---|---|
| `ivan@example.com` | `password` | Администратор |
| `maria@example.com` | `password` | Пользователь |

Тестовый счет для песочницы ТБанк - 40702810510000710417 

> **Порт 5432 занят чем-то ещё?** Частая проблема на Windows — нативно установленный Postgres-сервис перехватывает `127.0.0.1:5432` раньше, чем Docker успевает пробросить порт контейнера, из-за чего Liquibase падает с ошибкой авторизации, даже если креды в `.env` верные. Проверьте `netstat -ano | findstr :5432` (Windows) — если listener не один, либо остановите нативную службу, либо разведите порты (например, `5433:5432` в `docker-compose.yml` + `DB_PORT=5433` в `.env`).

> **"Error response from daemon: network ... not found" при запуске compose с несколькими `-f`?** Осиротевшая Docker-сеть от предыдущего неполного `down` или смешивания разных вариантов запуска (`docker compose up -d postgres` отдельно, потом полный стек с `-f`). Чинится через `docker compose -f docker-compose.yml -f docker-compose.monitoring.yml down`, при необходимости — `docker network prune -f`, и запуск заново. Держите одну и ту же команду запуска постоянно, не чередуйте варианты без промежуточного `down`.

### Мониторинг (Prometheus + Grafana)

Отдельный стек, запускается вместе с основным через два `-f`, чтобы попасть
в одну Docker-сеть:

```bash
docker compose -f docker-compose.yml -f docker-compose.monitoring.yml up -d --build
```

- Prometheus: http://localhost:9090
- Grafana: http://localhost:3000 (admin / admin при первом входе)

**Actuator/metrics-эндпоинты (`/actuator/**`) вынесены на отдельный порт 9091**, который **не публикуется** наружу в `docker-compose.yml` — снаружи он физически недостижим, доступен только внутри Docker-сети (именно так его достаёт Prometheus, обращаясь к `app:9091`). Основной порт 8080 отдаёт только само приложение.

Подробности — в [`monitoring/README.md`](monitoring/README.md).

## Локальный запуск без Docker

Нужен установленный PostgreSQL 16 и Java 17.

```bash
# создать базу и пользователя вручную, либо поднять только postgres из compose:
docker compose up -d postgres

mvn spring-boot:run
```

Конфигурация подключения к БД в `application.yaml` берётся из переменных
окружения с дефолтами (`DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USERNAME`,
`DB_PASSWORD`) — без Docker подставятся дефолты, указывающие на
`localhost:5432`.

Схема БД создаётся автоматически при старте приложения через Liquibase
(`src/main/resources/db/changelog/`) — накатывать SQL руками не нужно.

> **Меняли уже применённый changeSet вручную?** Liquibase хранит контрольную сумму каждого применённого changeSet в `public.databasechangelog` и откажется катить миграции дальше при расхождении. На локальной dev-базе, если применённый changeSet ещё не ушёл в общий git/прод, можно просто снести volume (`docker volume rm finance-tracker_postgres-data`) и накатить заново. На проде так делать нельзя — только новый changeSet поверх.

## Интеграция с банками (T-Bank / T-API)

Приложение умеет импортировать операции по дебетовым/расчётным счетам
через [T-API Т-Банка](https://developer.tbank.ru/docs/api/t-api) —
режим "только чтение", без каких-либо платёжных операций со стороны
приложения.

### Текущий статус — важно понимать реальные границы

**Сервисный слой готов и покрыт тестами.** UI для привязки счёта и запуска
синхронизации реализован — форма привязки на `/bank-integration/link`
(со вспомогательной кнопкой для быстрой подстановки тестового счёта
песочницы), кнопка синхронизации на странице счёта

Сейчас интеграция работает **только с песочницей** T-API
(`https://business.tbank.ru/openapi/sandbox/...`). Продовое
подключение требует регистрации юрлица/ИП и OAuth2-авторизации через
T-ID с согласием пользователя — отдельный этап, не реализован.

### Архитектура

Общий принцип — Adapter/Strategy: у каждого банка свой "сырой" формат
ответа, но вся остальная логика приложения работает только с
нормализованным DTO, не зависящим от конкретного банка. Добавление
второго банка — это новый коннектор с тем же интерфейсом, без изменений
в остальном коде.

- `service/BankConnector.java` — общий контракт для любого банка.
- `service/Impl/TBankConnector.java` — реализация под Т-Банк: HTTP-запрос
  к песочнице, курсорная пагинация (`nextCursor`), перевод
  банковского формата (`typeOfOperation: Credit/Debit`, цифровой код
  валюты ISO 4217) в нормализованный вид.
- `DTO/BankTransactionDto.java`, `DTO/BankStatementResult.java` —
  нормализованные DTO, не зависящие от банка.
- `DTO/TBankStatementResponseDto.java`, `DTO/TBankOperationDto.java`,
  `DTO/TBankBalancesDto.java` — "сырые" DTO под формат ответа Т-Банка.
- `service/BankImportService.java` / `service/Impl/BankImportServiceImpl.java` —
  привязка счёта (`linkAccount`), синхронизация транзакций с
  дедупликацией и обновлением баланса (`syncTransactions`).
- `config/TBankProperties.java` — конфигурация (URL, токен).

### Хранение в БД

Связь "внешний банковский счёт ↔ ваш `Account`" — строго 1:1, поля
прямо в `accounts` (без отдельной таблицы-связки):
`bank_code`, `external_account_number`, `last_synced_at`. Для счетов,
созданных вручную, все три поля `NULL`.

Дедупликация транзакций — через `external_source`/`external_id` в
`transactions` с unique-constraint. Postgres не считает два `NULL`
равными, так что constraint не мешает обычным вручную созданным
транзакциям (у них оба поля `NULL`) — срабатывает только при попытке
повторно импортировать одну и ту же банковскую операцию.

### Настройка

```
TBANK_API_TOKEN=TBankSandboxToken
```

в `.env` (без слова `Bearer` — префикс добавляется в коде; регистр
токена важен — именно `TBankSandboxToken`, с заглавной `B`).

### Известные ограничения текущей реализации

- **UI отсутствует** — привязка счёта и синхронизация доступны только
  программно.
- Тип операции (`INCOME`/`EXPENSE`) определяется по `typeOfOperation`
  банка (`Credit`/`Debit`) — более гранулярная классификация (переводы
  между своими счетами, комиссии, кэшбэк отдельно от обычного расхода)
  не реализована.
- Баланс привязанного счёта перезаписывается значением из ответа банка
  (`balances.balanceEnd`) только при синхронизации "до текущего
  момента"; при историческом бэкфилле баланс не трогается.
- Ручные операции (пополнение/снятие/создание транзакции вручную) на
  счетах, привязанных к банку, **пока не заблокированы** — это
  осознанно отложенное решение, а не забытая деталь. Риск: ручная
  операция создаст запись, которой не будет при следующей
  синхронизации, баланс и история могут разойтись с реальными данными
  банка.
- Параметр курсора пагинации (`cursor` в query) реализован по
  документации без проверки на реальном многостраничном ответе —
  требует подтверждения на живой песочнице при накоплении там
  достаточного числа операций.
- Юнит-тесты `BankImportServiceImplTest` покрывают сервис импорта через
  моки `BankConnector`. HTTP-слой (`TBankConnector`) отдельными
  тестами (WireMock/аналог) пока не покрыт — зависимость для этого в
  `pom.xml` не добавлена.
- Формат ответа песочницы T-API может меняться без предупреждения
  (прямое предупреждение из документации T-Bank) — сырые DTO стоит
  сверять с актуальным ответом перед каждым существенным изменением
  интеграции.

## Тесты и покрытие кода

```bash
mvn clean verify
```

Прогоняет полный набор тестов и генерирует отчёт JaCoCo:

```
target/site/jacoco/index.html
```

Тесты разделены на два уровня:

- **Unit-тесты** (`*Test.java`) — сервисы через Mockito, контроллеры через standalone MockMvc. Быстрые, не требуют внешних зависимостей.
- **Интеграционные тесты** (`*IT.java`) — поднимают настоящий PostgreSQL через **Testcontainers** (требуется запущенный Docker daemon) и проверяют то, что unit-тесты в принципе не видят: `JOIN FETCH`/lazy-loading на реальном Hibernate-контексте, поведение `@Version` при конкурентных изменениях счёта. Именно эти тесты ловят классы багов вроде `LazyInitializationException` и потерянных обновлений при гонке — замоканный репозиторий никогда не воспроизведёт такое поведение.

## Структура проекта

```
src/main/java/com/finance/finance_tracker/
├── controller/       # Thymeleaf-контроллеры + REST-контроллер CurrencyController
├── service/           # интерфейсы сервисов (с Javadoc), включая BankConnector/BankImportService
│   └── Impl/           # реализации, включая TBankConnector/BankImportServiceImpl
├── repository/        # Spring Data JPA репозитории (+ проекции вместо HashMap-агрегаций)
├── entity/             # JPA-сущности (LAZY-связи, equals/hashCode по id, @Version на Account)
├── DTO/                # объекты передачи данных, включая нормализованные и "сырые" банковские DTO
├── mapper/             # MapStruct-мапперы DTO <-> Entity
├── config/             # конфигурация (Security, OpenAPI, Web, Cache, TBankProperties)
├── aspect/             # AOP-аспект аудита
├── handler/            # глобальный обработчик исключений
├── exception/          # кастомные исключения
└── Util/               # утилитные классы (форматирование валют, security-хелперы)

src/main/resources/
├── db/changelog/       # Liquibase changelog (схема БД + seed-данные + банковская интеграция)
├── templates/           # Thymeleaf-шаблоны
├── static/               # CSS/JS
└── application.yaml     # конфигурация приложения

src/test/java/          # unit-тесты (*Test.java) и интеграционные тесты (*IT.java)

docs/                    # дополнительная документация (протокол запуска, план миграции)
monitoring/              # конфигурация Prometheus/Grafana
```

## Известные ограничения

Список того, что осознанно не доведено до идеала на данный момент —
чтобы не удивляться при код-ревью:

- Курсы валют кэшируются (`@Cacheable`) без TTL и без graceful fallback при
  недоступности внешнего API — при падении `exchangerate-api.com`
  соответствующие страницы (дашборд, счета) вернут 500 вместо деградации.
- Расчёт агрегированного баланса пользователя реализован **дважды** независимо — в `UserService.getUserTotalBalanceInRub` (используется контроллерами) и в `AccountService.getTotalBalance`/`getTotalBalanceInCurrency` (не используются нигде, кроме тестов). Требуется решить, оставлять ли обе реализации.
- Банковская интеграция (T-Bank) — только чтение, только песочница, без UI (см. [раздел выше](#интеграция-с-банками-t-bank--t-api) для полного списка ограничений).
- Страница редактирования счёта (`/accounts/{id}/edit`) не позволяет менять баланс намеренно — для этого есть отдельные операции пополнения/снятия.
- Нет rate limiting/anti-bruteforce на `/login` и `/register`.
- Нет восстановления пароля по email.
- CI/CD не настроен — сборка и тесты запускаются только вручную (`mvn clean verify`).

## CI/CD

Не настроен — сборка и тесты запускаются только вручную (`mvn clean verify`). Тесты не требуют ручной настройки `.env`/локальной БД (см. [Тесты и покрытие кода](#тесты-и-покрытие-кода)), так что подключение к GitHub Actions/аналогичному CI технически несложно — если Docker доступен в раннере, `mvn clean verify` пройдёт без дополнительной подготовки окружения.
